# Fork 上游同步与自有版本发布

保留 fork 的定制行为，持续同步上游，并为消费方提供可追溯的自有 tag。本 Skill 不绑定特定账号、组织、项目、语言或包管理器，可由本地 agent 或 CI runner 调用。Skill 本身不提供调度器，也不会自动配置凭据或启动监控。

## 识别目标与项目约定

先读取目标仓库作用域内的 `AGENTS.md` 或等价说明，检查分支、remote、工作区及已有任务。执行 commit、push、PR 前重新阅读贡献规范与 PR 模板。不要把安装 Skill 的目录当成要同步的项目，也不要直接修改包管理器的依赖缓存或其他自动生成的 checkout。

按当前请求、项目已确认的配置、Git remote 及托管平台的 fork 元数据确定以下信息。沿用已有约定，不要求用户为使用 Skill 新建配置文件：

| 信息 | 识别依据 |
| --- | --- |
| 自有仓库与写入目标 | 用户指定目标、现有 push remote 及仓库身份 |
| 上游仓库 | 项目配置的 upstream remote 或托管平台记录的直接父仓库 |
| 双方同步分支 | 用户或项目约定优先，其次查询双方实际默认分支，两边可以不同 |
| 待保留的定制 | 已确认记录及 fork 相对已合入上游基线的有效差异 |
| 版本范围与发布单元 | 项目现有版本约定，多包仓库需区分目标包及其 tag 前缀 |
| 自有版本标识 | 沿用项目已确认的自有 tag 规则，未约定时使用中性的 `fork` |
| 验证方式 | 目标项目当前 CI、贡献规范或用户已确认的检查命令 |

* 用实际仓库身份匹配 remote。远端不一定名为 `origin` / `upstream`，上游分支也不一定是 `master` / `main`，不要从本地功能分支推断同步分支。输出和来源注释使用去掉认证信息的仓库标识，不携带 remote URL 中的 token 或密码。
* GitHub 可查询 fork 的 `parent`，其他平台使用其可用 API 或 Git remote。没有 Connector 时使用可用 CLI 或本地 Git，不强制依赖某个插件或托管平台。
* 对于普通仓库、镜像、多个上游或分叉链，只有来源能唯一确定时才继续。无法确定上下游、写入目标或版本范围时，先完成只读检查，再集中说明缺少的信息，不猜测或改写 remote。
* 结合提交图、合并历史、完整 diff 和调用路径识别有效定制，不把所有 ahead 提交或作者不同的提交都当成自有补丁。将可解释的现有定制作为本次保留基线，涉及含义不明的业务变更时再确认。
* 运行中识别的仓库地址、账号、真实 SHA、业务定制和本机路径属于目标项目上下文，不回写到通用 Skill。项目专有记录由项目自身维护，分发 Skill 不携带这些记录、凭据或私有数据。

## 确定任务范围

* **检查**只读取状态并给出候选方案。只说“检查”或“试运行”时，不修改源码、分支、tag、暂存区或远端。
* **同步**准备上游合并，并按已授权的范围提交、push 或更新 PR。**发布**在验证后创建自有版本 tag。
* 安装 Skill 不代表授权同步、发布或配置调度。当前任务或定时任务保存的指令明确授权后连续执行，不重复询问已授权事项。
* 元数据与写操作优先使用当前可用且符合项目约定的工具。拉取对象、合并和补丁操作使用 Git。平台能力不足时使用可用 CLI，不把工具名称写成接入前提。

## 检查上游与实际差异

1. 查询双方远端同步分支、HEAD 和相关 tag，不能把本地缓存、锁文件或上次运行的 SHA 当成远端最新结果。网络或权限失败时停止依赖该信息的操作。
2. 分别检查上游新提交和新版本 tag。用 merge-base、完整文件列表及 diff 区分上游变化和 fork 定制，不仅报告 ahead/behind 数量。
3. 读取上游 tag 时保留来源区分，可在隔离仓库中使用独立 ref 命名空间。不把上游原名 tag 直接推到 fork，也不覆盖自有 tag。带注释 tag 需解析到实际 commit。
4. 默认将去掉可选 `v` 前缀后的 `X.Y.Z` 作为稳定版本，按语义化版本比较。项目使用包名前缀或其他版本体系时沿用其明确规则，不把其他包的 tag 混入目标包。预发布及无关 tag 只报告，除非用户指定采用。
5. 上游分支有变化但未发 tag 时，可以执行已授权的同步及分支快照发布，不必等待上游发版。正式 tag 和分支快照的来源选择见下节。

## 日常分支同步

* 从远端自有同步分支创建或复用合适的隔离 checkout / worktree。不切换或清理用户的开发分支，不 stash、reset 或提交无关的未完成修改。
* 将上游同步分支合入候选，保留自有提交。默认使用 merge，不通过 rebase 或 force push 重写已推送历史。
* 遇到冲突时阅读双方改动和调用方，做保留原有定制意图的最小调整。不用全量 `ours` / `theirs` 覆盖解决冲突。
* 上游已提供等价行为时可以删除重复补丁，并说明等价证据。业务或接口含义不明确时，不自行决定新行为。
* 阅读完整合并结果及相对自有基线的完整 diff，执行 `git diff --check` 和项目约定检查。能确定意图且检查通过时按授权继续，无法确定或验证失败时保留候选和证据，不发布 tag。
* 已授权 PR 时复用同一任务的已有 PR。push 前重查远端目标分支，发生并发变化时更新候选并重新检查，不覆盖其他提交。

## 选择发布来源

默认采用已确定的上游同步分支快照。用户明确要求严格基于上游正式 tag 时，使用正式 tag 模式。“检查 / 同步 / 发布”与来源选择相互独立，选择来源不扩大操作权限。

### 分支快照

* 固定本次实际采用的上游分支 commit SHA。候选准备、验证和发布围绕这个 SHA，不在过程中静默切换到新的分支 HEAD。
* 在该 SHA 历史中选择可达的稳定 tag 作为版本参照。沿用项目已有选择约定；没有约定时，用 `git rev-list --count <tag-commit>..<upstream-commit>` 的计数衡量距离，选计数最小者，计数相同时按项目版本规则选较高者。不采用其他发布线不可达的最新 tag；没有可用参照时报告缺失，不编造版本号。
* 候选包含固定的上游 SHA 和有效自有定制，可复用符合要求的自有同步分支。不为发布而退回旧 tag、丢弃已同步的上游修复。
* 分别阅读参照 tag 到上游 SHA、上游 SHA 到自有候选的完整差异，区分上游未发版变化和自有定制。检查提交图，处理候选中固定 SHA 之外无法解释的上游变化。
* 上游未发版变化也要纳入兼容性及回归检查。仅证明上游 SHA 是候选祖先，不能证明定制完整或候选可用。

### 正式 tag

* 使用用户指定的 tag，未指定版本时使用目标发布单元的最新稳定 tag，并解析到实际 commit SHA。
* 以该 tag 为代码基线，只移植经确认的自有定制和必要打包文件。后续可延续可追溯的自有发布分支，但不盲目移植全部 ahead 提交。
* 阅读候选相对上游 tag 的完整 diff，每处代码差异都要能归于定制或必要适配。此模式不包含 tag 之后的上游代码。
* tag 缺少补丁依赖的 API 时，不自行升级基线、删除补丁或切换为快照。报告原因，必要时准备适配 PR。

## 自有 tag 命名与发布

沿用目标项目已确认的命名约定。没有约定且采用 SemVer 时，默认标识为 `fork`，可在调用参数或项目配置中替换为自有标识；不从账号或组织名自动推导。示例：

| 来源 | 默认 tag 示例 |
| --- | --- |
| 正式 `v1.2.3` 或 `1.2.3` | `1.2.3-fork.1` |
| 以 `1.2.3` 为参照的上游 `master` 快照 | `1.2.3-fork.master.1` |
| 以 `1.2.3` 为参照的上游 `main` 快照 | `1.2.3-fork.main.1` |

* 分支字段使用实际**上游**分支名，不使用本地功能分支或自有发布分支名。分支含 `/` 等不能直接用于 SemVer 的字符时，使用项目已约定的版本标识映射，未约定则先确认映射，不静默合并不同分支的版本序列。
* 相同版本参照、自有标识、发布来源和上游分支下，有效代码或打包内容变化才递增末尾编号。新的可达版本参照使用新的版本前缀。上游移动既有 tag 时停止该来源发布并报告，不用新编号掩盖来源变化。
* 查询远端自有 tag 和来源记录，核对来源 SHA、定制及有效打包内容。同一来源内容已发布时不重复发版，只有 Skill 或维护说明变化也不递增项目版本。发布重试复用同一版本，不因 push 失败递增编号。
* 示例后缀属于 SemVer 预发布标识，不是上游正式版本。消费方根据包管理器规则显式固定自有版本；不依赖 `master` / `main` 字符串排序推断时间。名称含分支名的版本 tag 仍按版本引用。
* 完成项目验证后，创建带注释的自有 tag，指向已推送到自有仓库、包含定制的候选 commit。已授权的 push 使用单个明确 tag refspec，不使用 `--tags`、force 或删除重建既有 tag。

tag 注释使用实际运行数据记录来源：

```text
Upstream-Repository: 本次确定的上游仓库身份
Upstream-Source: branch 或 tag
Upstream-Branch: 实际上游分支名，仅 branch 来源填写
Upstream-Tag: 版本参照 tag
Upstream-Tag-Commit: 参照 tag 对应的完整 commit SHA
Upstream-Commit: 本次固定采用的完整上游 commit SHA
Fork-Commit: 完整候选 commit SHA
Customizations: 保留或调整的定制
Validation: 当前候选实际执行的检查与结果
```

快照模式以 `Upstream-Commit` 为代码基线，tag 只作版本参照；正式 tag 模式中两个上游 commit SHA 相同。旧 tag 缺少来源时先核对提交图和内容，不移动旧 tag，也不无证据推断基线。

## 按目标项目验证

* 根据实际语言、构建系统、包管理器和发布单元检查源码、manifest、入口、公共 API、资源及打包范围，不强制存在某个文件或使用某个命令。多包仓库只覆盖本次目标及实际受影响的依赖。
* 例如 SwiftPM 项目需检查 `Package.swift`、版本相关 manifest、library products、资源、headers 和平台约束；版本化消费涉及的直接及传递依赖不能保留 `branch` / `revision`。其他包管理器按其自身规则检查，不套用 SwiftPM 的限制。
* 对照已确认定制复核调用方、数据格式、错误语义和执行顺序。区分静态检查、依赖解析、编译、测试和运行验证，不能用一种结果替代另一种，也不能复用较早候选的通过结果。
* 执行当前项目约定且已授权的验证命令。无人值守发布前应已确定适用的构建和回归检查；没有编译步骤的项目使用其实际验收方式，不机械新增构建要求。验证缺失、受阻或失败时完成不受影响的检查和候选准备，不自动发布 tag。
* 不为继续流程添加空测试或把文本匹配当成行为验证。验证后修改过候选时，重跑受影响检查。
* 不顺带升级下游项目的依赖声明或锁文件，也不将创建 Git tag 等同于上传包到 registry、部署或应用商店发布。这些操作各自需要任务授权。

## 调用与定时运行

用户可以只提供目标目录并要求检查，由 agent 识别其余上下文。信息已有可靠来源时不重复询问；确实缺少时只确认影响当前操作的必要项。自有标识、上游和分支等参数也可通过调用指令或项目现有配置提供，不必修改通用 Skill。

定时任务需明确目标、频率、任务范围、发布来源、允许的外部操作及验证方式。Skill 文件存在不代表调度、网络、仓库凭据或 runner 已就绪，不自行创建这些配置。

有变化时简短报告实际来源及 SHA、版本参照、自有候选 SHA、定制保留情况、验证结果、PR 或最终 tag，以及阻塞点。发布后核对远端 tag 指向。周期检查无变化时保持安静，未变化的待处理问题不重复创建 PR 或提醒。
